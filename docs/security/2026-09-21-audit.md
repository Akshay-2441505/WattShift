# Security and bug audit, 21 September 2026

Scope: the whole repository (backend API, site agent, Kaggle runner, dashboard, deploy files, demo tooling). Method: read the
code and configuration, ran every existing test suite, ran a dependency audit and a secret scan, then wrote **active attack
tests** (`backend/tests/test_security.py`, 161 cases) that send hostile requests to the real API and fail if the server crashes,
lets a stranger in, or gives something away. Findings 1 to 11 and 15 were reproduced by a failing test before they were fixed.
Findings 12 and 14 are configuration hygiene, checked by reading. Finding 13 has a test, but it only runs on Linux, so it has not
been run on this Windows machine.

## Result in one line

15 findings: 1 high, 5 medium, 8 low, 1 plain bug. **All 15 are fixed and covered by tests.** Six risks remain by design or need
your accounts; they are listed at the end.

## Findings

Severity is what an attacker could do.

| # | Sev | Finding | Fix |
|---|---|---|---|
| 1 | HIGH | The agent accepted a plain `http://` cloud address. Its site key travels in a header, so anyone on the network path could read it and report as that site. It also followed redirects with the key attached. | `agent/wattshift_agent/config.py`: `http://` only for localhost. `client.py`: redirects are never followed; replies capped at 5 MB. |
| 2 | MED | A CSV upload with `NaN` GPUs, or a row with a missing field, crashed the parser with a 500. | `backend/app/backtest.py`: every case is a plain "line N: ..." message; sane upper bounds on job length and GPUs. |
| 3 | MED | An agent report containing a NUL character crashed the sync endpoint (Postgres cannot store one). | `agent_sync.py`: NUL rejected in free text; Slurm-shaped ids only. |
| 4 | MED | The job queue had no limit, and every Kaggle job now costs two GPU runs. A leaked key, or an open dev server, could flood the queue and burn the Kaggle quota. | `service.py`: at most `MAX_ACTIVE_JOBS` (default 50) waiting or running; the next one gets a 429. |
| 5 | MED | `PRODUCTION=1` was allowed together with `DEMO_MODE=1`, which exposes endpoints that delete every job and speed up the clock. | `main.check_production`: refuses to start. |
| 6 | MED | The audit trail could be edited or deleted by the application's own database login. | A database trigger refuses UPDATE and DELETE on `audit_log`; `init_db.py` installs it on existing databases. |
| 7 | LOW | The interactive API docs and the OpenAPI file were public on a hosted API, a free map of every endpoint. | Switched off when `PRODUCTION=1`. |
| 8 | LOW | No browser protections and no cap on request size. | API middleware (nosniff, no-frame, no-referrer, no-store, 413 above 6 MB). `frontend/vercel.json` adds a Content-Security-Policy, HSTS and permissions policy for the dashboard. |
| 9 | LOW | The public job list showed the owner's Kaggle username and kernel name. | Removed from the API and the frontend types. |
| 10 | LOW | A failure message could quote a local file path or a token from the Kaggle command's output, and the job list is public. | `app/safety.py` scrubs paths and token-like strings when written and again when read. |
| 11 | LOW | `repr()` of the settings object printed the API key and the database password. | Those fields are excluded from `repr`. |
| 12 | LOW | The demo's site key was saved inside the OneDrive-synced project folder. | Moved to `~/.wattshift/e2e-run`; the old key file was deleted; new files are owner-only. |
| 13 | LOW | The agent did not check who could read its site key file. | On Linux it refuses a key file readable by other users. |
| 14 | LOW | `.gitignore` did not cover `.env.*`, keys, certificates, logs or Kaggle credentials. | Extended. |
| 15 | BUG | A test for the demo's boundary timing was stale after the lead time changed to 230 s. | Test corrected. |

## What held up

- No SQL injection: every query is parameterised; the one f-string SQL builder (agent state) uses a fixed column list.
- No shell injection: `subprocess` is always called with an argument list, never `shell=True`; the agent can only run four
  allow-listed Slurm commands.
- No cross-site scripting: no `dangerouslySetInnerHTML`, `innerHTML` or `eval` anywhere in the dashboard.
- Write endpoints all refuse a missing, empty, wrong, near-miss and wrong-case key, and compare keys in constant time.
- Site keys are 256-bit random values stored only as SHA-256 hashes; a revoked key stops working at once; the operator key and
  a site key are not interchangeable.
- CORS gives a foreign website no permission unless its address is configured.
- 28 hostile job bodies, 17 hostile uploads (each sent twice), 19 hostile agent reports and 15 odd URLs never produce a server error.

## Risks that remain (not bugs; decide before real customer data)

1. **Read endpoints are open.** `/jobs`, `/sites`, `/sites/{id}/view`, `/measured`, `/savings/summary` and `/forecast` need no key.
   Fine for demo data; add a login before any real customer's job names or sizes are stored.
2. **One shared operator key.** Anyone holding `API_KEY` can change any site's mode or press its kill switch. There are no
   per-user accounts and no per-site scoping.
3. **No rate limiting.** Site keys are unguessable, so brute force is not realistic, but a flood of requests is not slowed.
   Use the host's protection (for example Cloudflare in front of Render) or add a limiter.
4. **The size limit trusts the `Content-Length` header.** A body sent in chunks without one is not capped by the app.
5. **Dependencies:** `pip-audit` is not installed here, so the Python packages were not checked against a vulnerability
   database (install with `pip install pip-audit`, then `pip-audit -r backend/requirements.txt`). There is no CI yet to run
   the tests and audits on every change.
6. **No key rotation flow** for site keys (revoking works; issuing a replacement is done by hand with `scripts/onboard_site.py`).
